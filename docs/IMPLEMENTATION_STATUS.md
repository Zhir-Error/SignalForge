# Implementation status

This review compares the actual repository with `SignalForge_Complete_Product_and_Engineering_Plan.md` and the user's master implementation request. The product plan is treated as the requirements source; instructions embedded in that plan are not separate authorization to deploy or perform external actions.

Status values follow the user's implementation request: **Not started**, **In progress**, **Implemented, awaiting verification**, **Verified**, or **Blocked**. `In progress` means the core path works while documented scope or verification gaps remain. `Blocked` is reserved for work that cannot proceed without an external dependency or decision. A `Verified` status applies only to the evidence and coverage stated in that row. This workspace has not been deployed as a production service.

## Workspace and environment

- Existing TypeScript/pnpm monorepo: Next.js web app, Fastify API, PostgreSQL/Drizzle, worker, verification runner, sample checkout service, shared auth/contracts/domain/AI packages, migrations, docs, and tests.
- Verification environment: Node.js 24.18.0, pnpm 11.20.0, PostgreSQL 18, and Docker Engine 29.9.2. The tenant database runs on local port 55432; the demo checkout uses a separate `signalforge_demo` database. Docker validation used a uniquely named Compose project and alternate published ports, leaving the existing Docker services untouched.
- No `.git` metadata is present, so repository history and committed-secret scans could not be checked. No external email or AI provider credentials were used. The ignored local `.env` had a runner secret containing `$`; it is now single-quoted so Compose preserves the configured value during interpolation.

```powershell
$env:POSTGRES_HOST_PORT = '55433'
$env:DEMO_POSTGRES_HOST_PORT = '55434'

docker compose -p signalforge-verify config --quiet

$images = @('api', 'web', 'worker', 'demo-service', 'verification-runner')
foreach ($name in $images) {
  docker image tag ('signalforge-' + $name + ':latest') ('signalforge-verify-' + $name + ':latest')
}
docker compose -p signalforge-verify up -d --no-build --force-recreate --wait --wait-timeout 180
# docker compose exec -T <api|web|worker|demo-service|verification-runner> id -u => 1000

After the worker outbox authorization change, the worker image was rebuilt and the Docker-backed smoke completed with persisted investigation evidence and `200 200 CHECKOUT_READY`. The final Compose config sets runner limits of 128 MiB, 0.5 CPU, and 64 processes, a read-only root, a 16 MiB no-exec/no-suid `/tmp`, dropped capabilities, and `no-new-privileges`; Docker inspection confirmed effective memory/CPU/PID, root-read-only, capability, and network settings. Write and external-IP probes were blocked while the registered recovery scenario passed. A second isolated run exercised poison-job retry exhaustion and Redis stop/start recovery. An initial read-only startup exposed Corepack cache writes, and the first isolated network excluded the worker; the runner now starts through Node directly and the worker joins the internal verification network. Both temporary Compose projects and volumes were removed. The production image still includes development dependencies and source files. A live OpenAI request, hosted GitHub Actions, external deployment, backup restore, and provider email delivery were not run.
