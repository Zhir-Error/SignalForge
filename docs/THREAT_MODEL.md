# Threat model

This is an implementation-level threat model, not a formal security assessment.

## Assets and boundaries

Assets include sessions, organization memberships, project API keys, telemetry, evidence, model credentials, verification requests, and audit records. Boundaries are the browser/API, API/database, API/outbox/worker, worker/provider, and worker/verification runner.

## Threats and implemented controls

| Threat                                        | Implemented controls                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cross-tenant object access                    | Session-derived actor, organization membership and role checks, scoped API access, composite organization keys, forced RLS, and non-owner PostgreSQL integration tests for project reads, correlation scoping, and cross-project ingestion. A complete route-by-route access matrix remains outstanding.                                                                                                                                                                                                                                                                                     |
| Stolen or replayed project key                | High-entropy project key, SHA-256 hash at rest, timing-safe comparison, project scope, expiry and revocation checks, `events:write` scope, configurable client-IP rate limits, and secret redaction.                                                                                                                                                                                                                                                                                                                                                                                         |
| Malformed or oversized telemetry              | Strict Zod schemas, body/batch/attribute limits, bounded timestamps, idempotency key, redaction, and content hashing.                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Prompt injection or sensitive data disclosure | Event text is treated as evidence data, known sensitive text and attributes are redacted, provider context is bounded, no model tools are exposed, and citations must reference persisted evidence for the investigation.                                                                                                                                                                                                                                                                                                                                                                    |
| Unsafe verification request                   | Fixed registered scenario keys, authenticated internal scenario endpoint, bounded database connection/query timeouts, and no shell or arbitrary command input. In local Compose, the runner uses a non-root account, read-only root filesystem, bounded no-exec temporary storage, dropped capabilities, no-new-privileges, CPU/memory/PID limits, and an internal network with only the worker and sample service; Docker smoke confirmed the runner can reach its registered check but cannot reach an external IP. Production-host enforcement and independent review remain outstanding. |
| Demo service access to tenant records         | The sample checkout connects only to a dedicated `DEMO_DATABASE_URL`; its recovery check executes `SELECT 1` and does not receive the tenant application database URL.                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Queue outage or duplicate delivery            | PostgreSQL outbox is transactionally committed with accepted work; outbox leases are reconciled after restart and duplicate correlation deliveries are idempotent. Before a Redis job runs or marks retries exhausted, its topic, payload, tenant, and claim status are matched against the durable outbox row. Unit regressions cover forged/stale jobs; Docker Redis/BullMQ checks cover the happy path, exhausted poison-job terminal state, and a queued job completing after Redis restarts. Broader production outage behavior remains unverified.                                     |
| Session theft, CSRF, or XSS                   | Better Auth HTTP-only cookies, trusted app origin, secure cookies in production, auth rate limits, Fastify security headers, escaped React rendering, and trusted-proxy IP configuration. Production proxy and TLS settings must be configured correctly.                                                                                                                                                                                                                                                                                                                                    |
| Invitation token leakage or misuse            | Only token hashes are persisted, invitations expire, token appears in a URL fragment, acceptance checks signed-in email, and invite roles cannot directly grant owner. Delivery is manual until mail is configured.                                                                                                                                                                                                                                                                                                                                                                          |

## Residual risks

No production deployment, external security review, or backup restore has been performed. Password reset and invitation email delivery are unavailable without a configured mail provider. Compose constrains the runner locally, but production-host enforcement and review have not occurred. Rate limits use a process-local store, so a multi-instance production deployment needs a shared store; client-IP behavior behind a proxy depends on `TRUSTED_PROXY_IPS` matching the actual proxy chain. The cross-tenant integration suite covers important data paths but not every API route, SSE revocation during an open stream, or every nested-resource combination. Organization deletion and audit-retention rules need a product-level retention policy before production use.
